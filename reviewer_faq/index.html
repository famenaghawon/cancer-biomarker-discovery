    Reviewer FAQ¶

    Answers to the questions a skeptical reviewer, hiring manager, or peer researcher is likely to ask when reading this repository. Each answer points at the concrete file or line of code that supports the claim, so nothing has to be taken on trust.

    Scope. The pipeline supports three data sources: synthetic expression (--data synthetic, default), real TCGA-BRCA (--data tcga_brca), and synthetic methylation (--data methylation). Answers below note which source each point applies to where relevant.

    Q1. Why does the default run use synthetic data? Why not default to real TCGA?¶

    Short answer: Reproducibility, offline capability, and CI speed.

    Long answer: The pipeline ships with three data sources and real TCGA-BRCA is a first-class path, not a demo afterthought:

    python scripts/run_pipeline.py --data tcga_brca

    That run downloads a curated BRCA subset (~40 MB) from the UCSC Xena Browser, caches it under data/cache/ (gitignored), and runs the exact same DE + ML + survival stack as the synthetic cohort.

    The default stays synthetic because:

    • CI runs on three Python versions and must complete in under a minute. A 40 MB network download, plus BRCA-scale computation, would push that to several minutes per version.
    • A fresh clone works offline. Synthetic data has no external dependency and no licence terms.
    • Synthetic data has a known ground truth — the recovery metric (top_k_recovery in analysis_summary.json) directly measures whether the pipeline found the planted biomarker panel. Real data has no such signal.

    That said, real data is where the pipeline proves itself. The TCGA-BRCA run loads 1,211 samples (1,097 tumour / 114 normal) across 59 curated cancer genes, fits a Cox proportional-hazards model on real clinical follow-up, and reports a concordance in the 0.5–0.7 range — the honest, non-trivial result you would expect from a real BRCA survival analysis.

    Why not stream from the GDC Data Portal directly? Because the GDC API requires authentication for most endpoints, and embedding a real subset in the repo raises redistribution concerns. UCSC Xena hosts the same TCGA data as plain HTTP files with no auth and an academic-friendly posture — that is why it is the loader's target. If the Xena URLs ever change, the loader falls back through a short list of alternatives in data_source/tcga.py.

    Q2. Isn't the classifier still suspiciously accurate on some sources?¶

    Short answer: The numbers are honest for each source. Synthetic sits at 0.75–0.83, methylation at 0.88–0.93, and real TCGA-BRCA at 0.96–0.97. Only the TCGA result looks "too good," and that is a real property of the cohort, not a bug.

    Long answer: Three data sources produce three different accuracy regimes, each with a distinct explanation:

    Source Typical accuracy Why
    Synthetic expression 0.75–0.83 Deliberately hard: effect_size = 0.5, ~20% silent tumours, ~25 decoy genes
    Synthetic methylation 0.88–0.93 Methylation signal is inherently cleaner (β-values are near-binary), but silent tumours and moderate effect size keep it from saturating
    Real TCGA-BRCA 0.96–0.97 Tumour-vs-normal classification on a curated 59-gene cancer panel; the signal is genuinely strong

    The synthetic cohorts are the hard ones by design. With effect_size = 0.5, ~20% silent tumours, and decoys, models should not hit 100%. If your synthetic run reports 0.95+, the data has drifted toward trivial separability — three knobs restore realism:

    1. DataConfig.effect_size — lower to 0.4 in config.py
    2. src/cancer_biomarkers/data_source/synthetic.py — raise per_gene_sd from U(0.4, 1.2) to U(0.8, 2.0)
    3. src/cancer_biomarkers/data_source/synthetic.py — raise the silent-tumour fraction from 0.20 to 0.30

    The hardness table in docs/methods.md §1 documents the expected range for each effect_size.

    The TCGA number is high because the task is easy on that cohort. TCGA-BRCA samples are almost all high-tumour-purity primary tumours versus adjacent-normal tissue, and the curated panel is built from genes known to be differentially expressed in breast cancer. A classifier that could not separate them would be broken. The interesting metric on TCGA is the survival concordance (0.525), not the classification accuracy.

    Q3. How do I know there is no data leakage?¶

    Short answer: Two code paths are audited and one test enforces it.

    Long answer:

    • Feature selection is computed on X_train only. See src/cancer_biomarkers/ml.py — _select_top_k(X_train, y_train, ...). The test fold is never passed to _select_top_k.
    • Cross-validation is run on the already selected training features (fast path) or re-selects inside each fold (nested path, nested_cv_evaluate). Neither path touches the test set during selection.
    • Test-set metrics are computed once at the end on X_test_k, which was never fed to any fitting or selection step.
    • Test enforcement — tests/test_no_leakage.py::test_select_top_k_ignores_holdout_labels constructs a dataset, mutates the hold-out labels, and asserts that the selected top-K does not change. If selection were contaminated by hold-out information, this test would fail.
    • Survival uses the same discipline: the Cox fit and Kaplan–Meier stratification are computed on the same samples the model was trained on, with no leakage into the DE or ML steps.

    The nested CV path exists because the fast path still has a small optimistic bias from selecting once before the outer CV loop. The methods doc (docs/methods.md §3) explains when to use which.

    Q4. Why Welch's t-test and not a negative-binomial GLM (as DESeq2 or edgeR do)?¶

    Short answer: The pipeline operates on continuous, log-scale values — not raw counts — so Welch is the appropriate test.

    Long answer: DESeq2 and edgeR model raw count data with a negative-binomial distribution to account for mean-variance dependence. The pipeline never sees counts:

    • Synthetic expression and TCGA-BRCA expression are provided as log2(norm_count + 1) — the standard Xena output. Continuous and roughly normal on a per-gene basis.
    • Methylation β-values are transformed to M-values via M = log2((β + ε) / (1 − β + ε)), which puts them on a continuous log-odds scale with broadly symmetric per-gene distributions.

    For continuous data, Welch's t-test is the standard test — it does not assume equal variances between groups, which is usually a bad assumption in tumour vs. normal comparisons.

    If you swap in real raw-count data, the correct move is to fit DESeq2 or edgeR directly. That would require a different data-load path (counts, not continuous values) and a different DE module. It is a genuine extension, not a drop-in replacement.

    Q5. Why Benjamini–Hochberg, and not Bonferroni?¶

    Short answer: BH controls the false discovery rate; Bonferroni controls the family-wise error rate. For genomics, BH is the field standard.

    Long answer: Bonferroni divides α by the number of tests, which is extremely conservative when you have hundreds or thousands of genes. You would miss real signal. BH controls the expected proportion of false discoveries among rejected hypotheses, which is what you actually care about in a discovery setting: "of the genes I call significant, at most X% are expected to be false positives."

    BH is implemented via statsmodels.stats.multitest.multipletests(method="fdr_bh") in differential_expression.py. It is the same correction used by DESeq2, edgeR, and limma for standard RNA-seq DE.

    If you want a more conservative test, multipletests also supports method="bonferroni" — one-line change, but not the default for good reason.

    Q6. Why log₂ fold change and not just "tumour mean / normal mean"?¶

    Short answer: log₂FC is symmetric, interpretable as "doubling / halving," and is the field convention.

    Long answer:

    • A ratio of 2 in one direction and 0.5 in the other are symmetric in log₂ (+1 and −1), but asymmetric in linear scale (2 and 0.5). Symmetry matters when you average across genes or rank by effect size.
    • "Doubling of expression" maps to a clean log₂FC = 1. That is why the default min_abs_log2fc = 0.6 corresponds to roughly a 1.5× change.
    • A difference of means (which the original version of this repo used) is not a fold change at all. Two genes with the same difference-of-means can have wildly different fold changes depending on baseline expression. On a log₂ scale, differences correspond to fold changes; on a linear scale, they do not.

    See differential_expression.py: log2fc = np.log2((tumor_mean + _EPS) / (normal_mean + _EPS)).

    Q7. How is the "top-K recovery" metric computed, and why does it matter?¶

    Short answer: It counts how many of the top-K selected features are in the planted true-biomarker panel. It only applies to synthetic sources, which have a known ground truth.

    Long answer: Accuracy tells you whether the classifier works, but not whether it found the right thing. A model can be 95% accurate while looking at the wrong genes. Recovery directly answers: "of the K features the pipeline selected, how many are the ones we planted?"

    Implementation (ml.py::count_true_in_top_k):

    true_set = set(true_biomarkers)
hits = [g for g in top_genes if g in true_set]
return {
    "k": len(top_genes),
    "n_true_in_top_k": len(hits),
    "true_hits": hits,
    "recovery_rate": len(hits) / max(1, len(true_set)),
}

    The result is written to analysis_summary.json under top_k_recovery and logged at the end of the pipeline. Typical recovery on the synthetic cohort is around 11–12 of 25 biomarkers, and on methylation around 25 of 25 (the methylation signal is cleaner).

    Real TCGA-BRCA has no ground-truth panel, so recovery is not reported for that source. The true_biomarkers field for TCGA is simply the curated gene panel that the loader requested, not a signal that was planted. That distinction is reported honestly in the summary.

    A companion test (tests/test_biomarker_recovery.py) asserts that at least a third of the true biomarkers appear among the significant DE genes under default-like settings — if feature selection were broken, this test would fail.

    Q8. Why fixed hyperparameters instead of a grid search?¶

    Short answer: Reproducibility and CI speed.

    Long answer: A grid search adds a nested loop that changes the selected hyperparameters based on the fold split. Two runs of the same script could produce different models, which makes the pipeline's outputs non-deterministic from a reviewer's perspective. It also multiplies the run time by the number of grid points (often 5–20×), and the CI runs three Python versions.

    The current design uses:

    • Logistic regression C = 0.1 (mild L2 regularisation; enough for 30 features without overfitting)
    • Random forest max_depth = 5, min_samples_leaf = 5, n_estimators = 200 (shallow trees, no overfitting)

    nested_cv_evaluate in ml.py is the natural home for a hyperparameter search — the inner loop of nested CV is exactly where the search should live. Adding GridSearchCV there is a ~10-line change and would not affect the smoke-path CI.

    The trade-off is documented in docs/methods.md §7 (Limitations).

    Q9. Why two classifiers, and not a deep learning model?¶

    Short answer: The right model for the data, and the right model for the reader.

    Long answer:

    • Data size. 200 samples × 500 genes is well within the regime where regularised linear models (logistic regression) and shallow ensembles (random forest) are competitive with deep models. A neural network on 200 samples would overfit without heavy regularisation and extensive tuning.
    • Interpretability. Logistic regression coefficients directly indicate which genes push toward tumour vs. normal. Random forest importances give a complementary, non-linear view. Both are straightforward to explain in a methods section. A deep model's "importance" is a post-hoc approximation.
    • Domain convention. The biomarker-discovery literature overwhelmingly uses linear / tree-based models for expression-based classification. A demo that mirrors that convention is more useful than one that chases a trend.

    Adding a third model (e.g. SVM, gradient boosting) is a two-line change in ml._make_models. It is not added by default because two classifiers already demonstrate the pipeline's modelling surface and keep CI fast.

    Q10. What would you do differently if this were a real study?¶

    Short answer: Six concrete changes, in priority order.

    Long answer:

    1. External validation cohort. The pipeline already runs on real TCGA-BRCA data, but a real study would validate on a second independent cohort (e.g. METABRIC for BRCA, or a GEO series) and report performance on that. A single-cohort result is a starting point, not evidence.
    2. Batch-effect correction applied by default. The --batch-correct flag exists and the batch.correct_batch function is tested, but the default is off. A real study would run the flag on and compare, or fit a model with batch as a covariate directly.
    3. Proper survival modelling. The lifelines Cox fit currently uses only 2–3 prognostic genes; a real study would fit a multivariate model on a larger panel selected by univariate screening, report HRs with 95% CIs, and validate the stratification on the external cohort.
    4. Nested cross-validation throughout. Report performance from the outer CV of a properly nested design; the current nested_cv_evaluate is the starting point and only runs when CB_RUN_NESTED_CV=1.
    5. Pre-registered thresholds. Fix α, min |log₂FC|, and effect-size cutoffs before looking at data. Post-hoc threshold tuning is the most common source of irreproducible biomarker results.
    6. Wet-lab validation. The ultimate test. No classifier result, however clean, replaces an assay.

    Points 1–4 are implementable inside this repo as extensions; 5 and 6 are study-design decisions, not code.

    Q11. Is this "pharmaceutical-grade" as the original description claimed?¶

    Short answer: No, and neither the README nor the docs claim it.

    Long answer: The original repo description used language like "pharmaceutical-grade" and cited performance metrics (92.4% accuracy, "450+ biomarkers") that came from a single synthetic run. Those claims have been removed:

    • The README's "Performance Metrics" section was replaced with an honest methodological description and a disclaimer.
    • The synthetic data was deliberately made harder (effect_size = 0.5) so models do not reach suspicious accuracy.
    • The methods doc and this FAQ are written to be auditable, not persuasive.
    • The real-data path is documented for what it is — a proof the pipeline works on public data, not a clinical-grade tool.

    "Pharmaceutical-grade" implies GxP-compliant processes, validated codebases, audit trails, and regulatory review. This is not that. What this repo is: a well-structured, tested, CI-verified example of correct methodology for a biomarker-discovery pipeline, running on both synthetic and public real data. That is a meaningfully different claim, and it is the honest one.

    Q12. I see a PROJECT_SUMMARY.md file. What is it?¶

    Short answer: A short changelog / summary of what changed from the original version of the repo.

    Long answer: PROJECT_SUMMARY.md documents the state of the codebase and the historical fixes applied to it. It is intentionally short and factual. For full methodological detail, use docs/methods.md; for figure descriptions, use docs/figures.md; for the answers to skeptical questions, use this file.

    The docs split responsibilities as follows:

    File Audience Content
    README.md anyone landing on the repo what it is, how to run it
    docs/methods.md a reviewer auditing the science formulas, thresholds, decisions
    docs/figures.md a reviewer reading the plots what each figure shows, how to sanity-check
    docs/reviewer_faq.md a skeptical reviewer this file
    docs/api.md someone importing the package public classes and functions
    docs/changelog.md anyone tracking version history release-by-release changes
    PROJECT_SUMMARY.md the maintainer what changed and why
